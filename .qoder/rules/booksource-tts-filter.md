# 书源与在线朗读 TTS 的收录口径

本条约束「往这个自用 Legado 里加书源 / 加朗读引擎」时的筛选标准。所有口径均由用户逐次点名确立，不要自行放宽。

## 一、书源

### 不收

| 类型 | 判定依据 | 确立时间 |
|---|---|---|
| 大厂正版站 | QQ阅读、潇湘书院、多看阅读（dkmi / duokan）、菠萝包轻小说（sfacg）、黑岩、宜搜、长佩、米读、免费追书（掌阅系）、腾讯浏览器、阅文系 xs8 | 2026-10-31 |
| 需要登录的源 | 有真实 `loginUrl` / `loginUi`，或正文、目录必须带登录态才拿得到 | 2026-10-31 |
| **言情 / 女性向为主的站** | 见下方判定方法 | 2026-10-31 |

### 「言情不要」的判定方法

不是「站点导航里出现过言情二字就删」——几乎每个综合站都有言情栏目，按这个口径会把书源删光。真正的判据是**该站是否以言情 / 女性向为主**：

1. 抓站点首页，统计导航区（`nav` / `menu` / `sort` / `channel` / `header` 容器 + 页面前段链接文字）里的类型词词频。
2. 女性向词表：言情、耽美、百合、女频、女生、女性、总裁、校园、宫斗、宅斗、快穿、豪门、高干、同人、肉文、少女、后宫、女尊、现言、古言、浪漫青春、古代言情、现代言情、幻想言情。
3. 男性向词表：玄幻、武侠、仙侠、都市、历史、军事、游戏、科幻、灵异、悬疑、奇幻、修真、网游、竞技、轻小说、恐怖、末世。
4. **判定**：女性向词频显著高于男性向（如 女105 : 男16），或男性向栏目数为 0 → 判为言情站，剔除。男性向占多数的综合站即使带「女生·言情」「耽美·纯爱」栏目也保留。
5. **站名直接是言情的**（如「言情小说」「飞言情网」）按名称剔除，即使站点实际是综合站——用户在书源列表里看到的就是这个名字。
6. 站点抓不到（证书过期、连接被拒/重置）时不下结论，标注「未取证」并保留，交给用户点名。

编码注意：GBK / Big5 站点用 `new TextDecoder('gbk'|'big5')` 解，`Buffer.toString('gbk')` 在 Node 下不可用。

## 二、在线朗读 TTS

### 只收

- **男声**
- **普通话**（排除粤语、四川话等方言，排除台普）

### 判定方法

- **性别不靠音色名猜**，用基频实测：TTS 返回 wav 时，30ms 分帧 + 自相关求中位 F0。实测分界很干净，男声 125–146Hz、女声 216–262Hz，取 **155Hz** 为界，155–180Hz 之间算边界待定需人工听。
- 只有 mp3、拿不到 wav 的接口无法测基频，按音色名与官方语音库文档判定，并在交付说明里标注「按名称判定，未测基频」。
- 名字中性的音色不能想当然：实测「思必驰川话」「AI 思必驰」「◇思必驰AI★+」都是女声（219–258Hz）。

### 语速参数陷阱

思必驰 `dds.dui.ai/runtime/v1/synthesize` 的 `speed` 是**反向**的：实测 speed=0.5 → 3.5 秒、1 → 7.1 秒、2 → 14.1 秒，值越大越慢；超出 0.5–2 会被服务端忽略、退回正常语速（所以 `speed=6` 等于正常语速）。想调快要用小于 1 的值。

### 编码层数

模板里 `java.encodeURI(java.encodeURI(speakText))` 套两层编码看着可疑，但实测无害：思必驰、百度翻译、讯飞 ekho 三家都会二次解码，单次 / 双重 / 完全不编码返回的音频字节完全一致。不必为此改模板。

## 三、内置到 App 的硬约束

产物要落进 `app/src/main/assets/defaultData/` 时，必须同时满足：

| 项 | 约束 | 机制依据 |
|---|---|---|
| 朗读引擎 id | **必须用负数** | `HttpTTSDao.deleteDefault()` 是 `delete from httpTTS where id < 0`；正 id 不会被当默认项清理，升级时既不清也不重置，会造成重复与漏管 |
| 书源类型 | **只放 `bookSourceType=0`（文本源）** | 文件源（=3）走的是另一套下载校验（`verify-file.js`），内置里混入会让用户在阅读页拿不到正文 |
| 大厂判定 | **按主域名末两段**，不是完整 host | 大厂资源常挂在子域：`g.hongshu.com`、`appi.kuwo.cn`、`reader.browser.miui.com`、`xiaoshuo.uc.cn`、`h5.17k.com`。只剥 `www/m/wap/api` 前缀会全部漏掉 |
| `contentType` | 留空即可 | `HttpReadAloudService` 里判的是 `ct?.isNotBlank() == true`，空值直接**跳过** MIME 正则校验；填错反而新增失败路径 |

内置书源不等于「装了就能用」：`importDefaultBookSources()` 只做 `bookSourceUrl !in existing` 的**增量插入**，从不删除。所以从内置里剔掉的源在**已安装**的设备上仍然存在，要在 App 里手动删或重装数据。

## 四、「有 loginUrl」不等于需登录

字段存在不能作为剔除依据，必须实跑：

- `loginUrl` 只是「本站有登录页，可选填」；`enabledCookieJar=true` 只是「愿意保存 cookie」，两者都不代表正文依赖登录态。
- 判定办法：**不带任何 cookie 跑三级验证**。实测 9 条 `jar=true` 的源里有 6 条匿名就三级全通（笔趣、壹二小说、阅读书库、kadokado、红薯网站、猫眼看书），得奇小说则 `content=false / 正文过短(0)`。
- 结论：**以实测为准，字段只做参考**。早期批次里标「可用」的源不能默认至今仍可用，要逐条重跑——栀子欢网、安之原创、轻之文库在同一天内就从可用变成 search 无结果。

## 五、正文校验只看长度会放过防爬乱文

三级验证的正文门槛是「去标签后 ≥100 字」，这条**拦不住服务端乱序防爬**：

- 实例：红薯网站 `g.hongshu.com` 匿名跑完整三级都 `stage:"ok"`（3 章 / 1416 字），但正文实际是
  「石溪镇上孩每训练都规律般情况下分两次次晨间训练次傍晚时候锻炼只过和傍晚时候锻炼相比」——字都在、语序全乱，人读不通。
- 这类源要靠人读一段，或加「常用词/标点密度」「句子通顺度」之类的启发式才能拦下。
- 因此报告「三级全通」时，必须同时给出 `contentHead` 供抽查，不能只报字数。

## 六、交付纪律

- 每一批筛选口径变化后，重算条数并同步更新 `legado-booksource/README.md` 里的文件名和条数，不能只改 JSON。
- 剔除的源要在 README 里列出「剔除了什么、依据是什么」，便于用户点名推翻。
- 产物一律落 `legado-booksource/`（已 gitignore），不放桌面、不进 git。该目录只留**一份可用书源 JSON + 一份 TTS JSON + 一份 README**，历史批次与中间取证数据不留在里面。
- 改名 / 改规则要同时落到**可用包 `书源-可用-NN条.json` 与内置 `bookSources.json`** 两处，并核对「内置文本源集合 == 可用包的 `bookSourceType=0` 子集」。文件源只在可用包里，不进内置。
- 删除本目录任何留档前，先全量镜像到 `D:\backup\` 并逐文件 MD5 校验；备份之后若又有并行会话写入（表现为「备份里没有的文件」），必须重新备份再删。

## 七、同名源必须消歧

App 书源列表显示的是 `bookSourceName`，多条同名没法分辨（也没法按名找站点）：

- 判定：同一包内 `bookSourceName` 出现 ≥2 次即需消歧。
- 写法：`原名(主机名)`，主机名 = 去协议、去 `www.`，**保留子域与 TLD**，例如 `笔趣阁(m.xinbqg.com)`、`玄幻阁乙(xuanyge.net)`、`阅友小说(sma.yueyouxs.com)`。
- 与既有先例一致（`书斋阁(shuzhaige)`）；需代理的源仍用 `(代)` 后缀，两个后缀可并存。
- 只改 `bookSourceName`，**不动 `bookSourceUrl`**（Room 主键，改了会产生重复条目并丢历史）。
- 消歧与剔除的依据直接写进 `legado-booksource/README.md`（逐条给站点与判据），不再另开 `recheck/` 留档目录。
